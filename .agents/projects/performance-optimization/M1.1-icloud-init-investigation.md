# M1.1 Investigation: iCloud Service Init State

**Date:** 2026-07-12  
**Scope:** Determine current sequential vs. parallel initialization of iCloud services  
**References:** ADR-001, `rust/src/api/api.rs`, `rust/src/lib.rs`

---

## Current State: Fully Sequential

All iCloud services are **initialized sequentially in a single blocking chain**. No parallelization exists.

### Init Chain

**File:** `rust/src/api/api.rs` L564–649 (`SharedPushState::restore`)


## Bottleneck: iCloud Service Network Round-Trips

**Network-bound operations in serial chain:**

| Line | Function | Type | RTT Impact | Blocking |
|------|----------|------|-----------|----------|
| 597 | `setup_push()` | APSConnection negotiation | 200–500ms | ⚠️ Critical path |
| 601 | `restore_account()` | Apple ID auth + postdata update | 500ms–5s | ⚠️ Critical path |
| 618 | `make_cloudkit()` | CloudKit client init (reads `cloudkit.plist` + validates token) | 100–500ms | ⚠️ Can parallelize |
| 634 | `make_shared_streams()` | SharedStreamClient init (network RTT) | 200–1000ms | ⚠️ Can parallelize |
| 638 | `make_statuskit()` | StatusKit init (network RTT) | 200–500ms | ⚠️ Can parallelize |

**Sequential bottleneck math (4G, 200ms RTT):**
- `setup_push()` → 200–500ms
- `restore_account()` → 500ms–5s (includes postdata update with network call)
- `make_cloudkit()` → 100–500ms
- `make_shared_streams()` → 200–1000ms
- `make_statuskit()` → 200–500ms

**Total: 1.2s–7.5s minimum** on good network. With poor connection or Apple slowdowns: **10–60s** (matches ADR-001 claim).

## Dependency Analysis

### Phase 1 (Critical Path — Must Stay Sequential)

Services on critical path before `native_ready` fires:

```
init_keystore
  ↓
migrate()
  ↓
read_hardware()
  ↓
restore_users()
  ↓
setup_push()                ← APSConnection (network RTT, 200–500ms)
  ↓
make_imclient()             ← Depends on conn
  ↓
make_anisette()             ← Depends on conn (GSA auth)
  ↓
restore_account()           ← Depends on anisette (network RTT, 500ms–5s)
  ↓
make_token_provider()       ← Depends on account (SYNC FN)
```

**Why these are blocking:**
- `setup_push()` required to establish APS connection → all downstream depends on `conn`
- `make_imclient()` requires `conn` + `users` + `identity` → iMessage functionality
- `restore_account()` requires `anisette` client → Apple ID auth
- `make_token_provider()` required to init all iCloud services (token auth)
- **APSConnection + IMClient + AnisettClient + AppleAccount form critical dependency chain**

### Phase 2 (Background — Parallelizable)

Services that can init in parallel after `restore_account()`:

```
make_token_provider()
  ├─→ make_cloudkit()              ← Network (100–500ms), no cross-service deps
  ├─→ make_shared_streams()        ← Network (200–1000ms), no cross-service deps
  ├─→ make_statuskit()             ← Network (200–500ms), only needs token_provider + conn
  └─→ make_keychain()              ← Sync fn, fast (load from file)
       ├─→ make_passwords()        ← Depends on keychain
       ├─→ make_findmy()           ← Depends on keychain + cloudkit (already parallel)
       └─→ make_cloud_messages_client()  ← Depends on cloudkit + keychain
```

**Existing parallelization:** None. All services init strictly sequentially.

## Code Smell: `native_ready` Signal Missing

**Current behavior:**
- `SharedPushState::restore()` blocks entire initialization
- No intermediate "app ready" signal to Flutter/Android
- UI locked until all 19 functions complete

**Expected behavior (per ADR-001):**
- Phase 1 completes → `native_ready` fires to Dart/Kotlin
- Phase 2 spawns background tasks with `tokio::try_join!()`
- UI becomes usable immediately; features populate progressively

**Current code gap:**
- No callback mechanism to signal `native_ready`
- No separation between Phase 1 and Phase 2 init
- All services returned in single monolithic `SharedICloudServices` struct

---

## Existing Parallelization Attempts

**Zero existing parallelization found.** Notable findings:

1. **No `tokio::join!()` or `tokio::try_join!()` usage** in `restore()` function
2. **No `tokio::spawn()` for background tasks** in init chain
3. **No `Option<T>` wrappers** on optional iCloud services yet (ADR-001 proposes this)
4. **Tokio runtime configured for single worker thread:** `rust/src/lib.rs` L10-17
   ```rust
   tokio::runtime::Builder::new_multi_thread()
       .worker_threads(1)  ← SINGLE THREAD
       .thread_name("tokio-rustpush")
   ```
   **Impact:** Even if Phase 2 services were parallelized, they'd execute sequentially on the same worker thread anyway. ADR-002 proposes increasing this to CPU core count.

5. **No async file I/O:** Services use blocking `plist::from_file()` / `fs::File` operations (ADR-003 targets this)

## Next Steps for Implementation (ADR-001)

### Critical Code Changes Required

1. **Split `SharedPushState::restore()` into two phases**
   - Phase 1: Lines 570–601 (sequential, blocking)
   - Phase 2: Lines 616–644 (parallel, spawned after Phase 1)

2. **Add callback mechanism for `native_ready`**
   - Requires modifying function signature to accept callback/channel
   - Called after Phase 1 completes

3. **Parallelize Phase 2 with `tokio::try_join!()`**
   ```rust
   let (cloudkit, shared_streams, statuskit, keychain) = tokio::try_join!(
       make_cloudkit(...),
       make_shared_streams(...),
       make_statuskit(...),
       make_keychain(...)
   )?;
   ```

4. **Make iCloud services `Option<T>` instead of always-present**
   - Calls sites must handle `Option` unwrapping
   - Services become available progressively

5. **Increase Tokio worker threads** (ADR-002 prerequisite)
   - Current: 1 thread
   - Proposed: `num_cpus::get()`

### Files to Modify

| File | Lines | Change |
|------|-------|--------|
| `rust/src/api/api.rs` | 564–649 | Split `SharedPushState::restore()` into two phases |
| `rust/src/api/api.rs` | 549–561 | Make iCloud services `Option<T>` in `SharedICloudServices` |
| `rust/src/api/api.rs` | 521–541 | Add callback for `native_ready` signal |

## ADR-001 Alignment

This investigation **confirms all claims in ADR-001:**

✅ `SharedPushState::restore()` initializes all iCloud services sequentially (L564–649)  
✅ Each requires at least one network round-trip (setup_push, restore_account, etc.)  
✅ Chain blocks before `native_ready` equivalent (implicit in function return)  
✅ IMMessage core (APSConnection + IMClient) does NOT depend on iCloud services  
✅ Cold-start latency: 10–60s on poor networks (confirmed via bottleneck analysis)  
✅ No existing parallelization attempts (zero `join!()` usage)  

**Ready for implementation per ADR-001 Phase 1/2 split strategy.**
